# Совместное планирование поездок

Простое решение на ASP.NET Core Web API и Blazor WebAssembly (.NET 8).

## Удаление категории предложений

Категория удалена из модели предложения, API, форм, списка предложений и PDF.
Плановый бюджет по-прежнему складывается из стоимости утверждённых предложений.
Подготовлена миграция `RemoveProposalCategory`, удаляющая столбец `Category` из `Proposals`.
Примените её из корня решения перед запуском обновлённого API:

```bash
dotnet ef database update --project TravelPlanner.Api --startup-project TravelPlanner.Api
```

## Что уже работает

Утверждённые предложения появляются в разделе расходов как заготовки. Кнопка «Добавить расход»
подставляет название и плановую сумму в форму. Остаётся выбрать плательщика, участников,
дату оплаты и способ деления; сумму можно уточнить. Балансы меняются только после сохранения.
Одно предложение можно связать только с одним расходом. После удаления расхода заготовка
появляется снова, если предложение всё ещё утверждено. Удаление предложения сохраняет сам
расход и доли, убирая только связь. Существующие расходы автоматически с предложениями не связываются.

Для связи подготовлена миграция `LinkExpensesToProposals`. Перед запуском обновлённого API
примените миграции командой `dotnet ef database update --project TravelPlanner.Api --startup-project TravelPlanner.Api`.

API поддерживает регистрацию и вход, поездки, приглашения, роли, предложения,
голосование, плановый бюджет, расписание, расходы, доли, балансы и возвраты.
Для поездок, предложений, событий, расходов и возвратов есть методы изменения и удаления.
Приглашение сохраняется в сервисе по адресу почты; отправки писем пока нет.

В Blazor есть вход и регистрация, список поездок, отдельные страницы создания,
изменения и удаления поездки, участники и роли, отправка и принятие приглашений,
предложения с добавлением, изменением и удалением, голосование и плановый бюджет.
Расписание, расходы, балансы и возвраты доступны и через API, и в Blazor.
В расписании организатор может переносить события на другой день мышью или менять дату
в обычной форме. При пересечении времени перенос отклоняется без изменения события.

Добавлены чат поездки через SignalR, комментарии к предложениям, карта отмеченных мест
и закрытый фотоальбом поездки. В деталях поездки есть навигация между разделами.

## Расписание, финансы и экспорт

- Расписание: `/trips/{tripId}/schedule`. Просмотр по дням, создание, изменение и удаление.
  Событие можно связать с утверждённым предложением. Перетаскивание на кнопку дня сохраняет
  время начала и длительность; обычная форма доступна для клавиатуры и сенсорного экрана.
  На странице явно используется UTC, как и в API. Переноса внутри дня по временной сетке нет.
- Расходы: `/trips/{tripId}/expenses`. Плательщик, дата, сумма, равное распределение или ручные
  доли. При редактировании показываются сохранённые доли, поскольку способ деления в БД не хранится.
  Участник вносит свои расходы; организатор может вносить и исправлять расходы любого участника.
- Расчёты: `/trips/{tripId}/balances`. Балансы, история возвратов и план рекомендуемых переводов.
  Кнопка «Подготовить возврат» только заполняет форму. Никакого обращения к банку нет.
  Запись сохраняется отдельной кнопкой после фактического перевода.
- Минимизация переводов: суммы считаются в целых копейках, сначала строится допустимый план,
  затем поиск с отсечениями пытается найти минимум. Ограничения: до 16 ненулевых балансов,
  200 000 узлов и около 250 мс поиска (время проверяется каждые 1024 узла).
  `settlement.isOptimal` истинно только после завершения поиска или достижения нижней границы.
  Если минимум не доказан, UI прямо это сообщает и показывает найденный допустимый план.
- PDF: `GET /api/trips/{tripId}/export/pdf`. Содержит даты поездки, расписание, отмеченные места
  и плановый бюджет. PDF формируется на сервере, шрифт с кириллицей включён в сборку.
  Используется PDFsharp 6.2.4 (MIT); шрифт Manrope (SIL OFL, лицензия в `Assets/Fonts`).
- Скачать файлы можно из деталей поездки и расписания. Запросы выполняются с JWT;
  файлы недоступны посторонним. Для скачивания не нужно запускать печать браузера.

Для этих изменений новые миграции не нужны: сущности и схема БД не менялись.
Если предыдущая `AddTripCollaboration` ещё не применена, её всё ещё нужно выполнить вручную.
После обновления запустите `dotnet restore`, перезапустите API и Blazor.

Проверки: `dotnet test TravelPlanner.sln`. По умолчанию API-тесты используют SQLite в памяти;
проверки конкурентных запросов требуют отдельной PostgreSQL. Браузерные проверки проведены
на изолированном стенде, включая две роли, переносы, конфликт времени, финансовые формы
и скачивание файлов. Ширины 390 и 320 px проверены в Chromium; это не заменяет проверку
клавиатуры и сенсорного ввода на настоящем телефоне.

## Чат, карта, комментарии и фото

Для этих функций подготовлена миграция `AddTripCollaboration`. После обновления исходников
примените её обычной командой из корня решения:

```bash
dotnet ef database update --project TravelPlanner.Api --startup-project TravelPlanner.Api
```

Приложение не применяет миграции автоматически. Новая миграция добавляет четыре таблицы:
`ChatMessages`, `ProposalComments`, `TripPlaces`, `TripPhotos`; существующие таблицы не удаляются.

- Чат: `/trips/{tripId}/chat`, SignalR endpoint `/hubs/trip-chat?tripId={tripId}`.
  JWT передаётся официальным .NET SignalR-клиентом. Подключение разрешено участникам;
  перед отправкой сервер повторно проверяет членство, сохраняет сообщение и доставляет
  его текущим участникам. История доступна через `GET /api/trips/{tripId}/messages`,
  по 50 сообщений с курсором `beforeId`. Клиент переподключается автоматически,
  при потере соединения текст не исчезает. Лимит сообщения: 2000 символов.
- Комментарии: `api/trips/{tripId}/proposals/{proposalId}/comments`, GET/POST/PUT/DELETE.
  Свой текст можно изменить и удалить; организатор может удалить чужой комментарий,
  но не переписать его от имени автора. Загрузка по 50 комментариев, есть обновление списка.
- Карта: `/trips/{tripId}/map`, API `api/trips/{tripId}/places`, GET/POST/PUT/DELETE.
  Место выбирается нажатием на карту или вводом координат. Сохраняются название и заметка.
  Автор и организатор могут изменить или удалить точку. Геокодирование и построение маршрута
  не реализованы. Leaflet 1.9.4 хранится локально вместе с лицензией, подложка OpenStreetMap
  загружается через интернет. URL тайлов можно заменить параметром `MapTileUrl` в клиентском
  appsettings.json. Стандартный адрес: `https://tile.openstreetmap.org/{z}/{x}/{y}.png`.
  Атрибуция остаётся видимой; нет предзагрузки или офлайн-копирования тайлов.
- Фото: `/trips/{tripId}/photos`, API `api/trips/{tripId}/photos`, GET/POST/DELETE,
  получение файла: `GET .../photos/{id}/content`. Загрузка через multipart/form-data,
  поля `file` и `caption`. Допускаются JPEG/PNG до 5 МБ, 20 мегапикселей и 8000 px по стороне,
  подпись до 300 символов; до 100 фото на поездку. Проверяются сигнатура и размеры,
  полноценного декодирования и антивирусной проверки сервер не делает. SVG не принимается.
  Фото хранятся в БД (`bytea`), а не по общедоступным URL. Для просмотра требуется JWT участника;
  автор или организатор может удалить файл. Браузер использует временные Blob URL,
  при уходе со страницы они освобождаются. Удаление фото и поездки удаляет данные без корзины.

Чат предназначен для обмена сообщениями внутри открытого приложения. Письма на почту,
push-уведомления, файлы в сообщениях и редактирование/удаление сообщений чата не добавлены.
Для публикации используйте HTTPS/WSS. В HTTP-логах не сохраняйте query string хаба:
в браузерном WebSocket-подключении он может содержать `access_token`.

Документация: [SignalR и JWT](https://learn.microsoft.com/aspnet/core/signalr/authn-and-authz?view=aspnetcore-8.0),
[Leaflet](https://leafletjs.com/reference.html), [правила сервиса тайлов OSM](https://operations.osmfoundation.org/policies/tiles/).

Клиент оформлен по образцу `TrainingAPI1/TrainingBlazor`: `ApiRequest/ApiRequest.cs`
с именованными методами, отдельные модели в `ApiRequest/Models`, `Services/CurrentUser.cs`,
страницы с `@bind`, `@onclick` и проверками роли. Ответ клиента содержит `status`, `data`
и сообщение об ошибке. API возвращает данные без обёртки — её добавляет клиент.
`TripFields` и `ProposalFields` — небольшие общие формы полей для страниц добавления и изменения.
Имена свойств клиентских моделей соответствуют JSON API, а не именам столбцов БД.

JWT и сведения о пользователе сохраняются в `localStorage`; после обновления страницы
вход восстанавливается. Пароль не сохраняется. При ответе `401` сессия очищается.
Роль берётся из участников конкретной поездки, а окончательная проверка прав остаётся на API.

## Первый запуск

1. Установите .NET SDK 8 и PostgreSQL, создайте пустую базу `travel_planner`.
2. Скопируйте `TravelPlanner.Api/appsettings.example.json` в `TravelPlanner.Api/appsettings.json`.
3. В созданном файле укажите строку подключения к своей базе и замените `CHANGE_ME` на пароль PostgreSQL. Для `Jwt:Key` задайте случайный секретный ключ длиной не меньше 32 байт; например, сгенерируйте его командой `openssl rand -base64 32`. Вместо записи ключа в файл можно задать переменную окружения `Jwt__Key`.
4. Из корня решения восстановите зависимости: `dotnet restore`.
5. Примените миграции: `dotnet ef database update --project TravelPlanner.Api --startup-project TravelPlanner.Api`. Если команда `dotnet ef` не установлена, установите инструмент EF Core 8: `dotnet tool install --global dotnet-ef --version "8.*"`.
6. Запустите API: `dotnet run --project TravelPlanner.Api --launch-profile http`.
7. В другом терминале запустите Blazor: `dotnet run --project TravelPlanner.Blazor --launch-profile http`.

Локальные `TravelPlanner.Api/appsettings.json` и `appsettings.*.json` исключены из Git. В репозитории хранится только `appsettings.example.json` без секретов. Настройка `TravelPlanner.Blazor/wwwroot/appsettings.json` содержит публичный адрес API и включена в репозиторий.

При дальнейших изменениях сущностей создавайте следующую миграцию командой
`dotnet ef migrations add НазваниеИзменения --project TravelPlanner.Api --startup-project TravelPlanner.Api`,
затем снова выполняйте `dotnet ef database update --project TravelPlanner.Api --startup-project TravelPlanner.Api`.
Первая миграция рассчитана на пустую базу; если таблицы уже были созданы вручную,
не запускайте первую миграцию поверх них. Для базы, созданной через миграции,
эта команда применяет только ещё не выполненные миграции.

Контекст находится в `TravelPlanner.Api/DatabaseContext/ContextDb.cs`: конструктор и `DbSet`.
Связи, индексы и точность денежных полей описаны атрибутами сущностей.
Модели оформлены по образцу `TrainingAPI1`: `User_Id`, `Trip_Id_Fk`, атрибуты
`Required` и `ForeignKey` над полями связей, свойства без начальных значений.
Атрибуты `Column` не используются: имена столбцов совпадают с именами свойств.
Миграция `UsePropertyNamesForColumns` переименовывает прежние столбцы и индексы,
обновляет внешние ключи без удаления таблиц и столбцов. Примените её обычной командой
`dotnet ef database update --project TravelPlanner.Api --startup-project TravelPlanner.Api`.
Навигационное свойство пользователя называется `User`. В `Repayment` две связи:
`Sender` — отправитель, `User` — получатель.
Проверки дат, ролей и сумм, а также значение по умолчанию для `Voting_Closed` заданы
в `InitialCreate` как настройки самой миграции и не входят в текущую модель контекста.
Чтобы изменить эти проверки, нужно явно добавить соответствующие операции в новую миграцию.

В профиле `http` API работает на `http://localhost:5101`, Swagger — по `/swagger`,
Blazor — на `http://localhost:5102`. Адрес API для клиента задаётся в
`TravelPlanner.Blazor/wwwroot/appsettings.json` (`ApiBaseUrl`). При смене адресов
обновите его и разрешённые адреса CORS в `TravelPlanner.Api/Program.cs`.
В Rider можно открыть `TravelPlanner.sln` и запускать оба проекта одновременно.

Для размещения приложения на сервере задавайте `Jwt__Key` и
`ConnectionStrings__Default` через переменные окружения. Локальный
`appsettings.Development.json`, если он используется, не публикуется в Git.

## Методы API

Для всех методов, кроме регистрации и входа, нужен заголовок `Authorization: Bearer <token>`.
Доступ к данным поездки есть только у её участников. Роль организатора задаётся внутри поездки.

Фильтр `CustomAttributes/RoleAuthorizedAttribute.cs` используется вместе с `[Authorize]`:
JWT проверяется стандартным обработчиком, затем фильтр проверяет пользователя и его роль
в таблице `TripMembers` для `tripId` из адреса запроса.

```csharp
[RoleAuthorized("Organizer")]
```

Так помечены управление поездкой, приглашениями, ролями, расписанием и утверждение предложений.
Для действий обоих участников используется `[RoleAuthorized("Organizer", "Participant")]`.
На методах без конкретной поездки `[RoleAuthorized]` проверяет только вход и наличие пользователя.
Недействительный JWT или отсутствующий пользователь дают `401`, неподходящая роль — `403`.
Роль читается из БД при запросе, поэтому её изменение не требует нового токена.
Отдельные проверки авторства расхода, возврата и предложения остаются в сервисах.
Таблица сессий и глобальные числовые роли для этого не нужны; схема БД не менялась.

| Адрес | Методы | Назначение |
| --- | --- | --- |
| `/api/auth/register`, `/api/auth/login` | POST | Регистрация и вход |
| `/api/trips` | GET, POST | Мои поездки, создание |
| `/api/trips/{tripId}` | GET, PUT, DELETE | Просмотр, изменение и удаление поездки |
| `/api/trips/{tripId}/invitations` | POST | Приглашение пользователя |
| `/api/invitations/mine` | GET | Мои ожидающие приглашения |
| `/api/invitations/{id}/accept` | POST | Принятие приглашения |
| `/api/trips/{tripId}/members/{userId}/role` | PATCH | Изменение роли; тело — строка `"Organizer"` или `"Participant"` |
| `/api/trips/{tripId}/proposals` | GET, POST | Предложения группы |
| `/api/trips/{tripId}/proposals/{id}` | PUT, DELETE | Изменение и удаление предложения |
| `/api/trips/{tripId}/proposals/{id}/vote` | PUT | Голос `value: 1` или `value: -1` |
| `/api/trips/{tripId}/proposals/{id}/status` | PATCH | Решение организатора: `Approved` или `Rejected` |

| `/api/trips/{tripId}/repayments` | GET, POST | Возвраты денег и добавление возврата |
| `/api/trips/{tripId}/repayments/{id}` | PUT, DELETE | Изменение и удаление возврата |

Организатор меняет поездку и расписание. Предложение меняет или удаляет его автор либо организатор.
Редактировать предложение можно до первого голоса и до принятия решения. Удаление предложения
сохраняет событие расписания, убирая ссылку на предложение. Отклонить предложение, связанное
с расписанием, можно после удаления этой связи.

Участник добавляет расходы от своего имени и меняет или удаляет расходы, где он плательщик.
Возвраты он отмечает от своего имени как отправителя. Организатор может вносить и исправлять
эти записи за любого участника. Удаление поездки удаляет её данные, но сохраняет учётные записи.

## Расписание

Тело POST и PUT содержит `title`, необязательный `proposalId`, `startAt`, `endAt`.
Например: `2026-11-01T13:00:00+03:00` будет сохранено как `2026-11-01T10:00:00Z`.
Время хранится в UTC; даты поездки и фильтр дня также трактуются по UTC.
Для просмотра одного дня: `GET /api/trips/1/schedule?date=2026-11-01`.
Ночное событие попадает в выборку каждого дня, с которым пересекается.

События должны находиться внутри дат поездки и не пересекаться друг с другом.
Интервалы 10:00–11:00 и 11:00–12:00 разрешены. Связать событие можно только
с утверждённым предложением этой же поездки. Изменить даты поездки так, чтобы
готовое событие оказалось за её пределами, нельзя.

## Расходы и возвраты

Расход содержит `title`, `payerUserId`, `amount`, `occurredOn` и `splitMode`.
Все суммы — в одной общей валюте поездки, с точностью до двух знаков; конвертации нет.
Название ограничено 200 символами, сумма — диапазоном `0.01`–`9999999999.99`.
Даты расходов и возвратов могут выходить за даты поездки, например при предварительной покупке билетов.

При `splitMode: "Equal"` укажите непустой `participantUserIds`. Поле `shares` оставьте пустым.
Плательщик не обязан входить в список людей, между которыми делится покупка.
Копейки остатка распределяются по возрастанию ID участников. Например, 100 на троих:
33.34, 33.33, 33.33. При `splitMode: "Custom"` передайте `shares` — объекты
`{ "userId": 2, "amount": 50 }`, а `participantUserIds` оставьте пустым.
Сумма ручных долей должна точно совпадать с расходом; нулевые доли допустимы.
Все указанные пользователи должны состоять в поездке, повторения не разрешены.
Способ деления используется для расчёта; в БД сохраняются сами доли.

Баланс = оплаченные расходы − собственные доли + отправленные возвраты − полученные возвраты.
Положительный баланс означает, что человеку должны деньги, отрицательный — что он должен группе.
Сумма балансов группы равна нулю. Баланс рассчитывается по текущим расходам и возвратам,
поэтому после изменения или удаления записи отдельное ручное обновление не требуется.

Возврат содержит `fromUserId`, `toUserId`, `amount`, `paidOn`. Отправитель и получатель должны
быть разными участниками. Сумма не может превышать ни долг отправителя, ни остаток к получению
у получателя. При изменении возврата его прежняя сумма исключается из расчёта проверки.
После исправления старого расхода ранее записанные реальные возвраты сохраняются;
балансы показывают новое состояние взаиморасчётов.

Основные ответы: `400` — некорректные данные, `401` — нет действительного JWT,
`403` — нет доступа, `404` — запись в доступной поездке не найдена,
`409` — конфликт расписания, состояния или одновременного изменения. При `409`
обновите данные и повторите действие. Операции сохранения расписания и финансов
выполняются в транзакциях EF Core.

Изменение ролей также выполняется в транзакции: два одновременных запроса не могут
понизить обоих последних организаторов. При голосовании предложение блокируется
через EF Core до сохранения голоса. Если организатор успел закрыть голосование,
запоздавший запрос не добавит и не изменит голос. При одновременных изменениях
API возвращает `409`, после которого нужно обновить данные.
При регистрации и приглашении проверяется формат почты, а не только наличие `@`.

## Проверка

`dotnet test TravelPlanner.Api.Tests/TravelPlanner.Api.Tests.csproj`

Проверки клиента: `dotnet test TravelPlanner.Blazor.Tests/TravelPlanner.Blazor.Tests.csproj`.
Оба набора сразу: `dotnet test TravelPlanner.sln`.
Клиентские тесты проверяют восстановление входа и выход, Bearer-заголовок,
формат изменения роли, обработку пустых ответов, ошибок входа и конфликтов API.

Тесты обращаются к настоящим контроллерам через HTTP с JWT. По умолчанию используется
SQLite в памяти. Проверяются права, хэширование, формат почты, расписание, деление сумм,
изменения и удаления, балансы, ограничения возвратов и каскадное удаление.

Для проверки на PostgreSQL задайте переменную окружения `TRAVELPLANNER_TEST_POSTGRES`
со строкой подключения к отдельному тестовому серверу и запустите ту же команду.
Тестовому пользователю нужны права создания баз. Для каждого сценария создаётся своя
база `travelplanner_test_<случайный идентификатор>`; после завершения она удаляется.
База из строки подключения не используется как хранилище тестов. Строка подключения
из `appsettings.json` при тестировании не используется.

Тесты одновременного изменения ролей, закрытия голосования и повторных голосов
выполняются только на PostgreSQL. Без этой переменной они помечаются как пропущенные.
Тестовые таблицы создаются из модели EF Core; это не заменяет проверку применения
миграций при первом запуске приложения. В этой доработке новые миграции не создавались.
Модели таблиц и `ContextDb` не менялись.

SignalR, PDF, карта, перенос событий между днями, комментарии, фотографии и расчёт
рекомендуемых переводов реализованы. Экспорт в календарь исключён из проекта.
